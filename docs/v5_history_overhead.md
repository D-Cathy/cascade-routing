# 历史库容量与控制开销

老师提出的两个问题需要分别验证：历史是否无限增长；节省的模型调用资源是否大于控制器开销。当前只能证明工程容量受控，尚不能证明净收益为正。

## 已实现的边界

在线 JointTransitionLibrary 仅接收白名单状态向量、预测收益、动作/历史类型、来源与记录ID、调用结果摘要和资源增量，不接收原始问题、答案全文或参考标签。原始资料与训练/评估文件是独立离线资产。库来自冻结的动态训练集，运行请求不会自动追加到库；当前方法不要求保存所有线上请求用于下一次决策。

默认最多10000条、序列化JSON载荷最多32 MiB，均可显式配置。超过任一限制在构造时拒绝，不静默删样本改变冻结策略。容量检查针对传入库，调用者预先加载的输入、Python对象、索引、完整训练数据和审计日志不包含在JSON字节限额内，因此这不是进程RSS硬限制或磁盘总量限制。向量维数和ID长度的开销也受载荷限制约束。

检索在初始化时按动作与有序历史建桶并预计算标准化向量，查询只计算对应桶的向量距离。继续采用精确检索、每来源最近一条、最多20组、至少5组支持及联合抽样；没有近似索引误差。候选排序仍为 O(N_b log N_b)，距离计算为 O(N_b d)，并非与库大小无关。初始化不应在每次决策时重新执行，应复用库实例。

容量应先在训练/调参阶段选择并冻结；若超限，需离线按训练集设计压缩或分层取样，再重新调参、校准。不得依据校准/测试结果删记录，也不得在已校准策略中滚动换库后沿用旧保证。本轮未实现自动持续学习。

## 日志和账本

实验reports与数据目录仍会随新增实验增长，本轮不删除它们，也没有给整库实现自动归档或TTL。部署前应单独制定原始文本的保留期限、审计日志轮转和冷存储策略，并测量磁盘占用。AttemptLedger防重复调用账本不能跟普通日志一起随意清理，否则会破坏每任务每模型至多尝试一次的约束。

## 如何判断是否抵消节省

现有 UnifiedExecutor 的 measured 控制耗时包含同步执行的评分、检索与规划；wall_clock 模式的总墙钟已含控制耗时，不要再加一次。simulation 固定控制开销不代表实测开销。每次请求可能多次决策，每次规划又可能多次检索，单次检索时间不能当作整个请求控制时间。

同一服务要求下比较完整策略与基线，货币净节省定义为：基线模型与通信费用减去本方法模型与通信费用，再减双方控制计算费用之差、存储费用之差、离线建库训练与索引构建的每请求摊销差。摊销分母应为事前声明的部署周期内服务请求数；时间、字节、货币、能耗先分项报告，只有明确费率才能换算，未知费率不能填零。

建议正式实验补充：库规模/容量扫描，完整控制器p50/p95/p99、超时率、评分/检索/规划分项，JSON与实际磁盘/RSS、冷启动及摊销、服务失败率和净费用；与共享评分器贪心等基线公平计账。只有净节省为正且满足同一质量/风险要求时才主张有效。容量与场景数调整须在校准之前完成。

## 本轮开发测量

脚本 scripts/benchmark_transition_overhead.py 使用100/1000/10000条合成记录，每规模预热10次、测量100次完整检索与联合抽样；不调用模型。报告 history_overhead_20261015_01/benchmark_isolated.json 记录JSON字节、索引数组字节、建库时长、tracemalloc建库峰值及检索p50/p95。合成向量只有2维，一个桶，不能代表正式任务嵌入或完整规划。tracemalloc峰值不含构造前输入，不是RSS。首次并发测试测量另存benchmark.json，保留环境抖动证据。不以这些微基准证明模型费用净节省，也未测量改造前速度，不能声称加速倍数。
