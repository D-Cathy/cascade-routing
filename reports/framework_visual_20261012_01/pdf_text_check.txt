公式翻译成中文


先记住一句话：质量收益 − 成本惩罚
方案得分 = 预测质量 − 成本重视程度 × 预测成本

τi(x) = q̂ i(x) − λ · ĉi(x)


 符号         怎么读               实际含义
 x/i        问题 / 模型编号         正在处理哪个问题、考虑哪个模型
 q̂ ĉ/      预测质量 / 预测成本       上方的小帽子表示估计值，并非已知真实结果
 λ          lambda，成本权重       把成本换成可与质量比较的惩罚；数值越大越节省
 τ          tau，方案得分          用于比较方案，越高越优；并不是成功概率
 S/H        候选模型集合 / 已调用集合    候选方案必须包含已调用模型，即 H ⊆ S
 符号       怎么读                  实际含义
 j / λj   当前阶段 / 该阶段的权重        调用后进入下一阶段，可以使用不同成本权重

 B/γ      平均成本预算 / 混合概率        本类 γ 是并列最优时选择较贵方案的概率


“超模型”就是一组候选模型
例如 S = {船端，岸端}：方案成本是两个模型成本之和，方案质量是“从两份答案中选最好”的预测价值。
当前轮只调用其中一个尚未运行的模型，拿到回答后重新决策。

 集合成本 = 各模型预测成本相加
 集合质量 = “取最高质量”之后，再求平均
 集合得分 = 集合质量 − 当前阶段成本权重 × 集合成本
为什么“先取最大值，再平均”顺序不能交换？
下面是解释计算顺序的假想例子，两个情形各占一半：

 假想情形              模型 A        模型 B         该情形的最大值
 情形 1              0.90        0.50         0.90
 情形 2              0.50        0.90         0.90

先取最大值，再平均：(0.90 + 0.90) ÷ 2 = 0.90。
先对每个模型平均，再取最大值：max(0.70, 0.70) = 0.70。

    这解释的是预测分布中的互补价值，不表示在线可以偷看真实质量。实际输出仍由已返回答案的质量预测决
    定；本地均值适配器没有协方差，集合质量退化为预测均值中的最大值。
  假设并列最优的便宜方案平均成本为 1，较贵方案为 3，目标平均预算 B = 1.5。选择较贵方案的概
  率 γ = (1.5 − 1) ÷ (3 − 1) = 0.25。
  这样混合的平均成本为 0.75 × 1 + 0.25 × 3 = 1.5。clip(..., 0, 1) 表示把计算结果限制在 0 到 1 之
  间。这个解释要求两个成本不同；相同时不能直接做除法，代码另行处理。
  它用于并列最优方案的预算混合，不是任意随机调用模型，也不是每条请求的硬预算保证。

2. 原论文的核心：在“模型集合”之间做路由
论文为 Jasper Dekoninck、Maximilian Baader、Martin Vechev 的 A Unified Approach to Routing and
Cascading for LLMs，ICML 2025，PMLR 267:12987–13010。官方页面。已将官方 PDF 下载到 本目录，并
提取为 文本。本次重点阅读 §§2–4 的决策定义、Algorithm 1–3、§5 和附录 D 的估计器设计，并与代码
对应；不声称完成附录所有证明的独立数学验证。

2.1 Routing：一次选一个模型
对输入问题 x，估计各模型质量 q̂ (x) 与成本 ĉ (x)，比较：
                              i             i




 τi(x) = q̂ i(x) − λ · ĉi(x)


             选择该值最大的模型。λ 越大，越重视成本。论文约束的是请求分布上的平均
Router._predict_model()

成本预算，不是每请求必不超预算。对应：论文 §2、Algorithm 1；router.py。

2.2 Cascading：固定顺序中的停止或继续
普通阈值级联依次运行模型，在当前答案的质量预测足够高时停止。 BaselineCascader 对应这种
thresholding baseline：第一步固定第一个模型，后续比较当前模型质量与 1 - lambda_ ，最终选择已运
行序列中最后一个模型。
论文还提出更强的固定顺序级联：比较继续到不同后续位置的集合价值，而不只看当前答案门槛。它在代码
中由 CascadeRouter(cascade=True) 实现，枚举固定前缀并强制紧邻继续。两者都属于 cascading，但决
策机制不同。对应：论文 §3、Algorithm 2；baseline_cascader.py、cascade_router.py。
2.3 Cascade Routing：允许初始选模、跳过模型和答案后再选
原方法把一组候选模型称为 supermodel，可译为“超模型”。它是一个模型集合及其答案选择规则，不是
把权重合并成新模型，也不做答案文本融合。
对集合 S，论文估计：

     q̂ S = E[maxi ∈ S q̃ i]

     ĉS = ∑i ∈ S ĉi

     τS = q̂ S − λj · ĉS


 表示估计不确定性下的质量量。当前已经调用的模型集合为 H，则比较的集合须包含 H。如果最优集合没
q̃
有新增模型，就停止；如果包含尚未运行的模型，就执行一个新增模型，再用实际回答更新估计。
三个模型初始最多有七个非空集合： {ship} 、 {shore} 、 {cloud} 、 {ship,shore} 、
{ship,cloud} 、 {shore,cloud} 、 {ship,shore,cloud} 。已调用船端后，只比较包含船端的集合。开
启向上顺序约束后，一旦跳过某低层模型，之后不能再回头调用它。
对应：论文 §4、Algorithm 3；cascade_router.py。理论上的一般框架允许更灵活的模型序列，论文也给
出先运行一个模型、再运行另一个较小模型的例子；本地船岸云协议明确限制严格向上，两者的动作空间不
同。
原文的最优性结论针对其定义的估计目标、成本约束和相应假设，不意味着预测器一定正确、真实服务绝对
最优或具有服务失败概率保证。

4. 深入核心函数：它每轮做了什么
入口 CascadeRouter.predict() 先调用质量和成本估计器，按已返回答案数确定阶段 j，选择当前阶段的
λ ，再进入 _predict_model() 。
 j


该函数的主要逻辑是：
   1. 收集非 None 的已运行模型，作为所有候选集合的共同基础。
   2. 用 models_to_evaluate 逐轮扩展未运行模型组合。
   3. 对每个集合调用 predict_supermodels() ，获得集合质量估计，再累加集合成本。
   4. 计算 quality_supermodel - lambda_ * cost_supermodel ，保留最优方案及并列项。
   5. 若开启 do_speedup ，按负边际收益检查剪掉部分扩展； max_depth 和 top_k_keep 限制搜索规
      模。
   6. 在并列最优集合中，依照 γ 选择便宜或昂贵的方案。该随机化用于预算边界，不是随机挑选任意模
      型。
   7. 最优集合没有新模型则返回 None ；否则返回其中一个待运行模型，本轮只执行它。
在 CascadeRouter 内，γ 是并列时选择较昂贵方案的概率，其拟合形式为：

 γ = clip((B − Ccheap) / (Cexpensive − Ccheap), 0, 1)


论文 Algorithm 1 对混合权重使用的方向与这个类不完全相同，不能不看定义就直接照搬变量含义；应以各
实现中的分支和公式对应解释。
已有模型的预测成本也出现在候选集合总成本中。在同一轮、同一历史下，它们属于候选间共同的已付出部
分；重要区别来自新增模型成本。实际请求记账仍需由调用方或执行器保存，预测成本不能覆盖真实已发生
费用。

这样，初始没有回答时是 ex-ante 预测；调用后可利用回答反馈进行 post-hoc 预测。级联的价值依赖调用
后是否获得足够有用的新信息。 如果生成后预测完全不变，系统虽然还能继续调用，决策却缺乏基于答案
内容调整的依据。
原 SWE-Bench 部分使用评估测试信息作为良好 post-hoc 估计场景，RouterBench 部分使用带噪声的真实
质量信号。本地研究若使用这些机制，必须明确哪些信息部署时真的能获得；不能把受控诊断结果直接当作
真实船舰服务能力。

7.1 状态与隐藏标签分开
schema.py 的 ObservableState 含原始问题、固定证据、可调用模型、已尝试与成功／失败／无效回
答、剩余时间预算、预测质量及当前环境。
UnifiedExecutor._make_state() 从已经发生的调用记录构造状态；真实质量、未调用答案不会复制进去。
即使回放进程拥有所有缓存输出，也只有执行到相应模型时才暴露该回答。最终选择器也只能从已调用且在
线检查成功的回答中选择。
 ModelStatus.SUCCESS 表示输出通过在线有效性检查，不等于质量已经达到门槛。 FAILED 表示尝试失
败， INVALID 表示调用发生但输出无效， UNATTEMPTED 表示未调用。这些状态影响重试限制和费用账
本，必须区分。

7.2 执行器统一管理动作与资源
UnifiedExecutor.execute() 每轮构造状态、运行策略、计入控制开销、检查动作，再调用模型。失败和无
效结果仍加入尝试历史并保留资源。发生资源未知时停止进一步花费，未知值不被写成零。
 _validate_call() 强制权限、未尝试和严格向上顺序。模型接口只读取同一原始 question 与
 evidence ，不接收前模型答案。


回放模式用输入的延迟和费用累计；真实后端必须使用 execution_timing="wall_clock" 与
 decision_timing="measured" ，用完整请求的单调时钟差计总时间，分项只作诊断，避免重复叠加。


但当前执行器尚不包含船岸云论文完整的预测上界动作筛选、保守停止门和多目标规划机制。代码中的
ACCEPT 表示终止并返回已选答案，不自动表示真实服务达标，须由终局评估判断。

7.3 终局评估是失败并集，缺失值保留未知
metrics.evaluate_terminal() 在选答已固定后读取标签，检查质量、时间、预算和有效答案；不会重新调
用模型或根据标签改选答案。
如果已知任一条件失败，结果就是失败；如果尚无已知失败但必要信息缺失，则结果不确定。
aggregate() 以全部请求为分母，存在未知结局时不伪造完整失败率，而是报告确定失败下界与可能失败
上界。这些上下界是缺失信息范围，不是统计置信区间。
8. 当前 CascadeRouterAdapter 到底实现了什么
cascade_adapter.py 保留原 CascadeRouter.fit/predict/select_answer 调用链，外面增加严格向上、
权限、失败占次数等适配。失败或无效尝试用非空哨兵表示，并赋极低预测质量，防止原代码把它当成尚未
运行或最终好答案。
但估计器是 DevelopmentMeanQuality 和 DevelopmentMeanCost ：只在 dev_fit 上计算每模型均值，在
线对所有任务基本返回同一组预测；质量没有协方差，λ 固定为零，不做参数搜索，只按拟合数据计算 γ。
适配器也显式拒绝其他估计器类型，尚不能直接换入任务专用估计器便宣称适配完成。
本次运行的配置给出：
  quality_means = [0.55, 0.78, 0.93]
  cost_means   = [1.00, 2.00, 3.00]
  lambdas      = [0, 0, 0]
  gamma        = 1/3




六条 dev_eval 任务都直接调用云端；两条成功、另有无效输出、资源超限以及标签／资源未知等诊断结
果。这说明原核心已接通执行器和评估，但示例未体现任务感知或回答质量感知的动态升级。它不能作为
v5 论文中强序贯基线或完整方法的性能复现。
 fixed_cascade_fallback 同样只耗尽固定顺序、返回最后有效答案，是明确命名的替代规则；它尚不是
论文中带训练评分器的固定阈值级联。
