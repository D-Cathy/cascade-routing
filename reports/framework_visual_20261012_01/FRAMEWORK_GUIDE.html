公式翻译成中文

先记住一句话：质量收益 − 成本惩罚

方案得分=预测质量−成本重视程度 × 预测成本
τi(x) = q̂i(x) − λ · ĉi(x)
符号怎么读实际含义
x / i问题 / 模型编号正在处理哪个问题、考虑哪个模型
q̂ / ĉ预测质量 / 预测成本上方的小帽子表示估计值，并非已知真实结果
λlambda，成本权重把成本换成可与质量比较的惩罚；数值越大越节省
τtau，方案得分用于比较方案，越高越优；并不是成功概率
S / H候选模型集合 / 已调用集合候选方案必须包含已调用模型，即 H ⊆ S
j / λj当前阶段 / 该阶段的权重调用后进入下一阶段，可以使用不同成本权重
B / γ平均成本预算 / 混合概率本类 γ 是并列最优时选择较贵方案的概率

“超模型”就是一组候选模型

例如 S = {船端，岸端}：方案成本是两个模型成本之和，方案质量是“从两份答案中选最好”的预测价值。当前轮只调用其中一个尚未运行的模型，拿到回答后重新决策。

集合成本 = 各模型预测成本相加
集合质量 = “取最高质量”之后，再求平均
集合得分 = 集合质量 − 当前阶段成本权重 × 集合成本

为什么“先取最大值，再平均”顺序不能交换？

下面是解释计算顺序的假想例子，两个情形各占一半：

假想情形模型 A模型 B该情形的最大值
情形 10.900.500.90
情形 20.500.900.90

先取最大值，再平均：(0.90 + 0.90) ÷ 2 = 0.90。
先对每个模型平均，再取最大值：max(0.70, 0.70) = 0.70。

这解释的是预测分布中的互补价值，不表示在线可以偷看真实质量。实际输出仍由已返回答案的质量预测决定；本地均值适配器没有协方差，集合质量退化为预测均值中的最大值。
γ 的公式如何理解？点击看一个预算例子

假设并列最优的便宜方案平均成本为 1，较贵方案为 3，目标平均预算 B = 1.5。选择较贵方案的概率 γ = (1.5 − 1) ÷ (3 − 1) = 0.25。

这样混合的平均成本为 0.75 × 1 + 0.25 × 3 = 1.5。clip(..., 0, 1) 表示把计算结果限制在 0 到 1 之间。这个解释要求两个成本不同；相同时不能直接做除法，代码另行处理。

它用于并列最优方案的预算混合，不是任意随机调用模型，也不是每条请求的硬预算保证。

2. 原论文的核心：在“模型集合”之间做路由

论文为 Jasper Dekoninck、Maximilian Baader、Martin Vechev 的 A Unified Approach to Routing and Cascading for LLMs，ICML 2025，PMLR 267:12987–13010。官方页面。已将官方 PDF 下载到 本目录，并提取为 文本。本次重点阅读 §§2–4 的决策定义、Algorithm 1–3、§5 和附录 D 的估计器设计，并与代码对应；不声称完成附录所有证明的独立数学验证。

2.1 Routing：一次选一个模型

对输入问题 x，估计各模型质量 q̂i(x) 与成本 ĉi(x)，比较：

τi(x) = q̂i(x) − λ · ĉi(x)

Router._predict_model() 选择该值最大的模型。λ 越大，越重视成本。论文约束的是请求分布上的平均成本预算，不是每请求必不超预算。对应：论文 §2、Algorithm 1；router.py。

2.2 Cascading：固定顺序中的停止或继续

普通阈值级联依次运行模型，在当前答案的质量预测足够高时停止。BaselineCascader 对应这种 thresholding baseline：第一步固定第一个模型，后续比较当前模型质量与 1 - lambda_，最终选择已运行序列中最后一个模型。

论文还提出更强的固定顺序级联：比较继续到不同后续位置的集合价值，而不只看当前答案门槛。它在代码中由 CascadeRouter(cascade=True) 实现，枚举固定前缀并强制紧邻继续。两者都属于 cascading，但决策机制不同。对应：论文 §3、Algorithm 2；baseline_cascader.py、cascade_router.py。

2.3 Cascade Routing：允许初始选模、跳过模型和答案后再选

原方法把一组候选模型称为 supermodel，可译为“超模型”。它是一个模型集合及其答案选择规则，不是把权重合并成新模型，也不做答案文本融合。

对集合 S，论文估计：

q̂S = E[maxi ∈ S q̃i]
ĉS = ∑i ∈ S ĉi
τS = q̂S − λj · ĉS

q̃ 表示估计不确定性下的质量量。当前已经调用的模型集合为 H，则比较的集合须包含 H。如果最优集合没有新增模型，就停止；如果包含尚未运行的模型，就执行一个新增模型，再用实际回答更新估计。

三个模型初始最多有七个非空集合：{ship}、{shore}、{cloud}、{ship,shore}、{ship,cloud}、{shore,cloud}、{ship,shore,cloud}。已调用船端后，只比较包含船端的集合。开启向上顺序约束后，一旦跳过某低层模型，之后不能再回头调用它。

对应：论文 §4、Algorithm 3；cascade_router.py。理论上的一般框架允许更灵活的模型序列，论文也给出先运行一个模型、再运行另一个较小模型的例子；本地船岸云协议明确限制严格向上，两者的动作空间不同。

原文的最优性结论针对其定义的估计目标、成本约束和相应假设，不意味着预测器一定正确、真实服务绝对最优或具有服务失败概率保证。

3. 原代码的接口与数据流

3.1 三个数据数组

以 N 条问题、M 个模型为例：

questions       # 长度 N，元素可为字符串或任务专用表示
model_answers   # N × M，未调用位置为 None
qualities       # N × M，估计器输出各模型的预测质量
costs           # N × M，估计器输出各模型的预测成本
sigma           # 每问题一个 M × M 协方差矩阵，或 None

model_answers 是最重要的信息边界。例如 [ship_answer, None, None] 只暴露船端回答，岸端和云端仍不可见。已有回答既用于评价该答案，也可以为未调用模型的预测提供反馈。

这些不是原始质量标签矩阵。训练或评估使用的 ground_truth_qualities 与在线预测值分开。原实验中的特殊 GroundTruth 估计器是噪声诊断设定，不应直接迁入真实路由器作为可观测输入。

3.2 两类 fit 的职责不同

quality_computer.fit(estimator_questions, all_answers, quality_labels)
cost_computer.fit(estimator_questions, all_answers, observed_costs)

router = CascadeRouter(quality_computer, cost_computer, models,
                       max_expected_cost=target_budget)
router.fit(tuning_questions, tuning_answers,
           ground_truth_qualities=tuning_labels,
           ground_truth_costs=tuning_costs)

前两次 fit 学习预测器；CascadeRouter.fit() 调整各阶段 λj 和并列最优方案的混合参数 γ。路由器的 fit 不会自动替你训练质量估计器。 trigger_training(True) 主要改变估计器的缓存／运行模式，也不等价于拟合预测器。utils.py、cascade_router.py。

原实验一般把训练数据前段用于估计器，后段用于策略参数搜索；RouterBench 的 GroundTruth 噪声实验另有特殊路径。这个“参数拟合”不应与船岸云论文中的独立失败风险校准混为一谈。

3.3 在线循环由调用方完成

answers = [None] * len(models)
while True:
    next_model = router.predict([question], [answers])[0]
    if next_model is None:
        break
    answers[models.index(next_model)] = invoke(next_model, question)

chosen_model = router.select_answer([question], [answers])[0]
chosen_answer = answers[models.index(chosen_model)]

predict() 返回的是下一模型名称或 None，本身不发 LLM 请求。select_answer() 返回最终答案所属的模型名称，调用方再取真实回答。代码不是一个调用 CascadeRouter 就自动管理全部模型服务的端到端应用。

原实验 utils.prediction() 实现上述循环，但 invoke 实际是从缓存 actual_answers[i][model_index] 取答案；质量标签在完成选答后用于计分。它是离线评估，不是模型现场生成。

4. 深入核心函数：它每轮做了什么

入口 CascadeRouter.predict() 先调用质量和成本估计器，按已返回答案数确定阶段 j，选择当前阶段的 λj，再进入 _predict_model()。

该函数的主要逻辑是：

  1. 收集非 None 的已运行模型，作为所有候选集合的共同基础。
  2. 用 models_to_evaluate 逐轮扩展未运行模型组合。
  3. 对每个集合调用 predict_supermodels()，获得集合质量估计，再累加集合成本。
  4. 计算 quality_supermodel - lambda_ * cost_supermodel，保留最优方案及并列项。
  5. 若开启 do_speedup，按负边际收益检查剪掉部分扩展；max_depth 和 top_k_keep 限制搜索规模。
  6. 在并列最优集合中，依照 γ 选择便宜或昂贵的方案。该随机化用于预算边界，不是随机挑选任意模型。
  7. 最优集合没有新模型则返回 None；否则返回其中一个待运行模型，本轮只执行它。

在 CascadeRouter 内，γ 是并列时选择较昂贵方案的概率，其拟合形式为：

γ = clip((B − Ccheap) / (Cexpensive − Ccheap), 0, 1)

论文 Algorithm 1 对混合权重使用的方向与这个类不完全相同，不能不看定义就直接照搬变量含义；应以各实现中的分支和公式对应解释。

已有模型的预测成本也出现在候选集合总成本中。在同一轮、同一历史下，它们属于候选间共同的已付出部分；重要区别来自新增模型成本。实际请求记账仍需由调用方或执行器保存，预测成本不能覆盖真实已发生费用。

4.1 不确定性为何重要

BaseQualityComputer.predict_supermodels() 调用 compute_expected_max()：

  • 没有协方差时，退化为模型预测均值中的最大值。
  • 有协方差时，代码使用 Sobol 样本、正态变换，以及独立或相关质量采样，近似估计最大值的期望。
  • 同一集合的模型预测存在相关性时，多个模型的互补价值与完全独立时不同。

E[max Qi] 通常不等于 max E[Qi]。如果把不确定性全部设为 None，集合价值的表达能力会明显改变。这是理解本地均值适配较弱的重要原因。

4.2 停止与最终选答是两件事

predict() 解决“是否值得继续花钱”；select_answer() 解决“已有的哪个回答更好”。后者只对实际返回的答案重新预测质量，选择预测分最高者，空历史返回 None。

因此，最后一个被调用的模型不必是最终输出模型。BaselineCascader 则采用最后一个已运行模型，两种选答规则不可混用。

5. 估计器层：通用算法怎样理解不同任务

原选择核心不限定答案必须是普通字符串。各任务把输入和输出转成自己的表示，再实现相同 predict() 接口。

ClassificationQualityComputer.prepare_data() 将完整训练输出按“哪些模型已运行”的不同子集遮蔽，再为目标模型生成学习样本；fit() 按目标模型和可见模型子集分别训练预测器。predict() 根据当前非空答案集合选择相应预测器及协方差。

这样，初始没有回答时是 ex-ante 预测；调用后可利用回答反馈进行 post-hoc 预测。级联的价值依赖调用后是否获得足够有用的新信息。 如果生成后预测完全不变，系统虽然还能继续调用，决策却缺乏基于答案内容调整的依据。

原 SWE-Bench 部分使用评估测试信息作为良好 post-hoc 估计场景，RouterBench 部分使用带噪声的真实质量信号。本地研究若使用这些机制，必须明确哪些信息部署时真的能获得；不能把受控诊断结果直接当作真实船舰服务能力。

6. 用一条实际运行的教学轨迹理解它

本次新增 trace_native_router.py，只构造合成质量预测和合成返回文本，直接调用原 CascadeRouter，不开启 LLM 推理。参数手动设定 λ = 0.5、γ = 0、无协方差，用于展示控制流程；它不是拟合模型或论文实验。

轮次已返回答案预测质量：船／岸／云下一动作
0全空0.70／0.85／0.90调船端

模型预测成本为 0.10／0.40／1.00。初始船端得分 0.70-0.5 × 0.10=0.65，岸端也为 0.65，并列时当前配置选择便宜集合，先运行船端。

船端返回后其质量预测降至 0.40，保留船端并增加岸端的集合得分为 0.85-0.5 × (0.10+0.40)=0.60，高于只保留船端的 0.35，因此继续运行岸端。岸端返回后，已有集合的得分为 0.86-0.5 × 0.50=0.61，增加云端后为 0.90-0.5 × 1.50=0.15，所以停止。

7.1 状态与隐藏标签分开

schema.py 的 ObservableState 含原始问题、固定证据、可调用模型、已尝试与成功／失败／无效回答、剩余时间预算、预测质量及当前环境。

UnifiedExecutor._make_state() 从已经发生的调用记录构造状态；真实质量、未调用答案不会复制进去。即使回放进程拥有所有缓存输出，也只有执行到相应模型时才暴露该回答。最终选择器也只能从已调用且在线检查成功的回答中选择。

ModelStatus.SUCCESS 表示输出通过在线有效性检查，不等于质量已经达到门槛。FAILED 表示尝试失败，INVALID 表示调用发生但输出无效，UNATTEMPTED 表示未调用。这些状态影响重试限制和费用账本，必须区分。

7.2 执行器统一管理动作与资源

UnifiedExecutor.execute() 每轮构造状态、运行策略、计入控制开销、检查动作，再调用模型。失败和无效结果仍加入尝试历史并保留资源。发生资源未知时停止进一步花费，未知值不被写成零。

_validate_call() 强制权限、未尝试和严格向上顺序。模型接口只读取同一原始 question 与 evidence，不接收前模型答案。

回放模式用输入的延迟和费用累计；真实后端必须使用 execution_timing="wall_clock" 与 decision_timing="measured"，用完整请求的单调时钟差计总时间，分项只作诊断，避免重复叠加。

但当前执行器尚不包含船岸云论文完整的预测上界动作筛选、保守停止门和多目标规划机制。代码中的 ACCEPT 表示终止并返回已选答案，不自动表示真实服务达标，须由终局评估判断。

7.3 终局评估是失败并集，缺失值保留未知

metrics.evaluate_terminal() 在选答已固定后读取标签，检查质量、时间、预算和有效答案；不会重新调用模型或根据标签改选答案。

如果已知任一条件失败，结果就是失败；如果尚无已知失败但必要信息缺失，则结果不确定。aggregate() 以全部请求为分母，存在未知结局时不伪造完整失败率，而是报告确定失败下界与可能失败上界。这些上下界是缺失信息范围，不是统计置信区间。

8. 当前 CascadeRouterAdapter 到底实现了什么

cascade_adapter.py 保留原 CascadeRouter.fit/predict/select_answer 调用链，外面增加严格向上、权限、失败占次数等适配。失败或无效尝试用非空哨兵表示，并赋极低预测质量，防止原代码把它当成尚未运行或最终好答案。

但估计器是 DevelopmentMeanQuality 和 DevelopmentMeanCost：只在 dev_fit 上计算每模型均值，在线对所有任务基本返回同一组预测；质量没有协方差，λ 固定为零，不做参数搜索，只按拟合数据计算 γ。适配器也显式拒绝其他估计器类型，尚不能直接换入任务专用估计器便宣称适配完成。

本次运行的配置给出：

quality_means = [0.55, 0.78, 0.93]
cost_means    = [1.00, 2.00, 3.00]
lambdas      = [0, 0, 0]
gamma        = 1/3

六条 dev_eval 任务都直接调用云端；两条成功、另有无效输出、资源超限以及标签／资源未知等诊断结果。这说明原核心已接通执行器和评估，但示例未体现任务感知或回答质量感知的动态升级。它不能作为 v5 论文中强序贯基线或完整方法的性能复现。

fixed_cascade_fallback 同样只耗尽固定顺序、返回最后有效答案，是明确命名的替代规则；它尚不是论文中带训练评分器的固定阈值级联。

9. 单条采集与评分链的定位

入口 single_task.py 的流程为：

validate 本地校验
  → collect 分别执行船、岸、云三个固定单模型请求
  → 保存原始输出与匿名评分卡
  → 双人评分及分歧裁定
  → evaluate 合并评估标签并重新计算终局指标

collect 是采集三模型数据，不是一条动态级联轨迹。每次独立调用均复用 UnifiedExecutor，以保证接口和记账一致；三个独立延迟不能直接拼成真实序贯网络轨迹。

真实后端的调用链为：

UnifiedExecutor
  → LiveModel.call_with_context
  → AttemptLedger.reserve（SQLite 持久化唯一尝试）
  → SingleHTTPTransport.send
  → http_once_worker.send_once（单次标准库 POST）
  → 解析、检查、记账并保存结果

PENDING 和已完成尝试都阻止同任务、同模型自动重发。worker 被本地超时终止，不意味着远端生成或费用已经取消。当前费用仅按 provider token fee 推导，不是 v5 的费用—传输归一化开销。

原 APIQuery 则是 LangChain／供应商 SDK 适配层，有多层重试路径；本地新后端避免走这条链。当前环境 APIQuery 的可选导入是否成功，应直接检查具体依赖，不能因为 import selection 成功就认为所有子模块都可用，因为 __init__.py 会捕获部分导入异常。
